# Cross-Project Environment Variable Handoff — September 2026
## Security boundary
This handoff intentionally contains **variable names and metadata only**. It contains no values, tokens, credentials, URLs, private keys, `.env` contents, or exported process environment. Retrieve values only through each project's approved secret mechanism.
## Evidence and scope
- **Vox:** `contracts/config/env-vars.v1.yaml` is the declared-name registry; `docs/src/reference/secrets-ssot.md` defines the Clavis-managed secret boundary.
- **FableForge:** `C:\Users\iacch\fableforge\.env.example` declares names; `convex/config/env.ts` is the required application access boundary.
- **GigMe:** `C:\Users\iacch\gigme\.env.example` declares names; `src/loadEnv.ts` owns local `.env` parsing.
- **GIGME:** no separately cased project root was found. It is treated as an alias of the on-disk `gigme` project, not as a second configuration plane.
- This is a declaration catalog, not evidence that any variable is populated or required in every environment.
## Value-recovery rules
1. Never copy a `.env` file, process-environment dump, token, key, password, or vault export into this document, source control, chat, or a shared drive.
2. Restore values project by project through an approved secret store or interactive, access-controlled process; validate presence without displaying values.
3. Keep public client configuration (`NEXT_PUBLIC_*` and `VITE_*`) separate from server-side variables. A public prefix is never suitable for a secret.
4. In Vox, use Clavis and `vox_secrets::resolve_secret(...)`. In FableForge, use `convex/config/env.ts`. In GigMe, use the `src/loadEnv.ts` contract.
