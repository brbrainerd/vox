# Orchestrator Chat Fast-Path, Reliability, and Latency Design

**Source:** live investigation during the Axis frontend remediation session
(2026-07-19/20) after fixing a chat-thinks-forever bug (the fleet's
`ProcessQueue` notify was silently dropped on a spawn-at-submit race with no
retry — commit `e7e2a09cea`). Fixing that surfaced the real problem
underneath: task submission now succeeds and executes, but every chat
message — including a one-line greeting — runs the full 6-phase agentic
pipeline built for genuine multi-step work. This document designs the fix
plus two adjacent problem classes (reliability gaps, latency waste) found by
independent read-only audits of the same code while investigating.

**Scope:** three independently landable phases, each with its own TDD cycle:
- **Phase A** — chat fast-path (new task category + dedicated processor).
- **Phase B** — reliability hardening (5 findings from a fresh orchestrator
  audit, ranked by severity).
- **Phase C** — latency fixes that apply to *every* task, not just chat
  (wire up an already-built but never-invoked compaction engine; parallelize
  a fleet-tick fan-out).

## Ground truth (verified by direct code reading, not inferred)

- Every task — regardless of origin — runs
  `[Inspect, Localize, Hypothesize, Act, Verify, Decide]` unconditionally
  (`crates/vox-orchestrator/src/runtime.rs:520-528`), one full LLM
  streaming call per phase (`run_phase_stream_with_bus`, `runtime.rs:259-318`).
  No category/complexity check gates this loop today.
- The phase prompt template embeds `"Known notes:\n{}"` (`runtime.rs:291`)
  built from `notes`, which is the **raw, unbounded concatenation** of every
  prior phase's output plus tool-call results (`runtime.rs:520, 607-610,
  660-661`) — resent in full on every subsequent phase. Token count and
  request payload grow monotonically phase-over-phase.
- `CompactionEngine::compact` (`compaction.rs:229`) already exists and does
  real truncation/summarization, and is already wired into the *session*
  transcript path (`session/state.rs:257`, `session/manager/mutations.rs:215`)
  — but is **never called** from the phase loop. `runtime.rs`'s only use of
  `CompactionEngine` is `estimate_tokens` for post-hoc cost telemetry
  (`runtime.rs:669-670`), after all 6 phases have already run.
- Nothing in the chat submit path distinguishes a chat message from an
  agentic task. `ChatPayload` (`crates/vox-gui/ui/src/types/tauri.ts:40-56`)
  → `SubmitTaskInput` (`crates/vox-gui/src/commands/control_plane.rs:11-36`)
  → daemon RPC params → `AgentTask::new` (`types/tasks.rs:711-719`) carries
  no category/source field; the only categorization mechanism (an
  `"[[category:X]]"` text marker scanned out of the description string) is
  never emitted by the GUI, so every submission — chat, slash command, skill
  deploy — defaults to the same category.
  `TaskCategory` is generated by `crates/vox-orchestrator/build.rs:109-146`
  from a plain string list at
  `contracts/orchestration/model-routing.v1.yaml:55-68` — adding a variant
  is a one-line config change, not a schema migration.
- `AgentFleet` holds exactly **one** `processor: Arc<dyn TaskProcessor>` for
  every agent, every task (`runtime.rs:913-929`), constructed once at
  startup as `AiTaskProcessor`. `TaskProcessor` (`runtime.rs:98-109`) is a
  single-method trait; `StubTaskProcessor` (`runtime.rs:112-129`, currently
  test-only) proves a minimal non-phased implementation is a well-worn
  pattern, not a novel one.
- The fleet tick runs every 1s (`D_1S`, `runtime.rs:1212`) and
  `nudge_queued_agents` (added this session, `runtime.rs:1017-1075`) is what
  wakes a freshly-spawned agent to dequeue its first task — meaning a first
  task can wait up to ~1s before dequeue even starts, on top of the LLM
  cost. This delay applies to every task type.
- The nudge's per-agent sends are still **serial** with a 5s timeout each
  (`runtime.rs:1029-1075`) — N wedged agents can stall a whole tick (and
  therefore `check_scaling`/`sync_fleet`/rebalance) by up to `N × 5s`.
  Already flagged by code review on the original fix; unaddressed in source.
- Drift state (`DriftState`, `budget/mod.rs`) is keyed only by `AgentId`,
  not `(AgentId, TaskId)`, and `reset_drift` (`budget/mod.rs:565`) has
  **zero call sites** anywhere in the crate — it is never invoked when a
  task completes or fails.
- The `HaltAgent` drift-circuit-breaker exit path
  (`runtime.rs:585-593`) does not call `abort_interrupted_task`, unlike the
  cancel path (`:533-536`) and the stream-error path (`:571-575`) right
  above it in the same function — the one path documented as an emergency
  breaker is the only phase-loop exit that skips the shared cleanup helper.
- `sync_fleet` aborts its *entire* per-tick pass with a bare `return` on a
  single agent's registry-lookup failure (`runtime.rs:967-977`), instead of
  skipping just that agent — a poisoned registry silently and permanently
  stalls fleet convergence for every agent, with only one log line.
- `ScaleDown`'s requeue of a retiring agent's remaining tasks discards its
  `Result` (`runtime.rs:1181-1187`, `let _ = submit_existing_task(...)`) — a
  failed requeue silently drops a task with nothing left tracking it.

## Phase A — chat fast-path

**Approach: new `TaskCategory::Chat` + a dedicated `ChatTaskProcessor`,
dispatched through a thin delegating wrapper.** (Two alternatives were
evaluated and rejected — see Non-goals.)

1. **Schema**: add `Chat` to `contracts/orchestration/model-routing.v1.yaml`'s
   `task_categories` list. `build.rs` regenerates the `TaskCategory` enum,
   `Display`, and `FromStr` impls automatically — no hand-written enum edit.
2. **Payload plumbing**: thread a category/source signal from the GUI's
   chat-submit path through to `AgentTask`. The cleanest point of truth is
   the composer's own submit call
   (`crates/vox-gui/ui/src/App.tsx` `handleLoquelaSubmit`) tagging the
   `ChatPayload` it builds — NOT inferred from `session_id` presence alone
   (slash commands and skill deploys also carry `session_id` through the
   same handler, so presence-of-session_id is not a reliable chat marker).
   Thread the tag through `SubmitTaskInput` → daemon RPC params →
   `AgentTask::new`, defaulting to the existing `[[category:X]]`
   text-marker convention if that's cheaper than a new field (decide during
   implementation by reading the exact current shape of each hop; the
   investigation traced every hop above with file:line, so this is a
   mechanical follow rather than new discovery).
3. **`ChatTaskProcessor`**: new `TaskProcessor` impl, one LLM call, a prompt
   written from scratch for a single-shot conversational reply (do NOT
   reuse the phase-loop's "Known notes" template — a single phase run in
   isolation against that template reads incoherently to the model, per the
   investigation's Option B rejection).
4. **`RoutingTaskProcessor`**: a thin wrapper implementing `TaskProcessor`
   that owns both `Arc<AiTaskProcessor>` and `Arc<ChatTaskProcessor>` and
   dispatches on `task.task_category` inside its own `process()`.
   `AgentFleet` continues to hold exactly one `Arc<dyn TaskProcessor>` (this
   wrapper) — no change to fleet construction, `resolve_route`, spawning,
   queueing, task history, dedup (`duplicate_of`), cost tracking, or the
   event bus. Chat keeps all of that infrastructure "for free," which is
   the whole reason Option C (bypass the orchestrator) was rejected.

## Phase B — reliability hardening (ranked by severity)

1. **Drift state not reset between tasks** (Important). Call
   `budget_manager.reset_drift(agent_id)` at both `complete_task` and
   `fail_task` transition points so a new task on a reused agent never
   inherits stale drift-fingerprint history from a prior, unrelated task.
2. **`HaltAgent` skips shared cleanup** (Important). Add the same
   `self.orchestrator.abort_interrupted_task(task.id, agent_id)` call the
   cancel and stream-error arms already make, for parity across all three
   phase-loop exit paths.
3. **`sync_fleet` aborts the whole tick on one agent's lookup failure**
   (Minor). Change the bare `return` to `continue` in the per-agent loop so
   one poisoned lookup doesn't silently stop fleet convergence for every
   other agent.
4. **Nudge fan-out is serial** (Minor, already flagged by code review).
   Fire per-agent `ProcessQueue` sends concurrently
   (`futures_util::future::join_all` or a bounded `FuturesUnordered`)
   instead of sequential `tokio::time::timeout` awaits, so N wedged agents
   cost one timeout window, not `N ×` timeout windows.
5. **`ScaleDown` requeue discards errors** (Minor). Log the error on a
   failed `submit_existing_task` requeue (matching the existing
   `complete_task`/`fail_task` logging pattern at `runtime.rs:867-887`) so a
   dropped task at minimum leaves a trace instead of vanishing silently.

**Non-goal for this plan:** the narrow, unconfirmed `sync_fleet` /
`check_scaling` registration-ordering race the reliability audit flagged as
"worth a closer look" but could not confirm as a real bug in the time
available. Not fixed here — recorded as follow-up debt, not designed
against speculation.

## Phase C — latency fixes (apply to every task, not just chat)

1. **Wire `CompactionEngine` into the phase loop.** Before building each
   phase's prompt, call `CompactionEngine::compact` on the accumulated
   `notes`/history the same way the session-transcript path already does,
   instead of resending it raw and unbounded. This is the single highest-
   leverage latency/cost fix found across both audits — the mechanism
   already exists and is proven correct elsewhere in the same crate; it is
   simply never invoked from the one place that needs it most.
2. **Parallelize the nudge fan-out** — same change as Phase B item 4; listed
   here too because its latency impact (bounding tick stall time) is
   distinct from its reliability framing (bounding blast radius of a wedged
   mailbox). Implemented once, satisfies both phases' acceptance criteria.

**Non-goals for this plan:** re-tuning provider/model default ordering
(Ollama-probe-first is a one-time ~2s cost at fleet construction, not
per-task — lower priority, not a live bug); reducing the fleet tick interval
below 1s; any change to `resolve_route`'s agent-selection scoring.

## Testing approach

- **Phase A**: TDD throughout. Unit tests for `ChatTaskProcessor` (single
  call, no phase loop, correct prompt shape) and `RoutingTaskProcessor`
  (dispatches `Chat`-category tasks to the chat processor, everything else
  to the existing `AiTaskProcessor`, verified via a spy/counting fake
  matching the `StubTaskProcessor` pattern already in the codebase). An
  integration-level test extending `chat_round_trip.rs` (added earlier this
  session) to assert a `Chat`-category submission completes with exactly
  ONE `TaskPhaseChanged` event instead of six — proves the fast path is
  actually taken, not just present in code. Zero LLM cost throughout (stub
  processors), consistent with the house rule against paid-call tests.
- **Phase B**: each of the 5 fixes gets its own unit test written red-first
  against the current buggy behavior (e.g. submit two tasks on the same
  agent with a drift-triggering fingerprint collision, assert the second
  task does NOT inherit the first's drift state after the fix).
- **Phase C**: a test asserting `notes` passed into phase N+1's prompt is
  the *compacted* form, not raw concatenation, once history exceeds the
  compaction threshold; re-run affected latency-sensitive tests to confirm
  no behavior regression in existing phase-loop tests.
- Every phase ends with the full `cargo test -p vox-orchestrator` (currently
  1026+ tests) plus the relevant frontend suite where Phase A's payload
  plumbing touches `crates/vox-gui/ui`.

## Non-goals (overall)

- No change to the 6-phase pipeline's actual phase *content*/prompts for
  agentic (non-chat) tasks — Phase A adds a parallel lightweight path, it
  does not modify the existing one.
- No reduction in phase count for agentic tasks — that pipeline's design
  (inspect/localize/hypothesize/act/verify/decide) is intentional for
  multi-step work; only chat-shaped input gets the fast path.
- No new GUI surface/UX changes beyond what's needed to tag a chat
  submission (Phase A item 2) — this is a backend/protocol change, not a
  composer redesign (the composer was already comprehensively reworked
  earlier this session).
