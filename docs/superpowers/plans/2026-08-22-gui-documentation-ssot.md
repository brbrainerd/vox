# Vox GUI Documentation SSOT Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give every user-reachable Vox GUI surface a one-sentence description that the app shows as a tooltip and the docs site renders alongside a CI-captured screenshot — from one field, so the two cannot disagree.

**Architecture:** `contracts/gui/surface-registry.v1.yaml` is already the SSOT for 107 surface entries, already generates `surfaceRegistry.generated.ts`, and is already CI-gated. Add a `description` field to the 32 entries that are real surfaces, extend the existing generator to emit it into both the TypeScript the app imports and a new generated markdown page, extend the existing gate to require it, and publish screenshots from the `@review-capture` Playwright sweep that already exists.

**Tech Stack:** Rust (`vox-cli` CI command), YAML contract, TypeScript/React (`vox-gui/ui`), Playwright, Astro/Starlight.

**Spec:** `docs/superpowers/specs/2026-08-22-gui-documentation-ssot-design.md`

## Global Constraints

- **32 surfaces, not 107.** `description` is required when `representation_tier != none` and **forbidden** when `tier == none`. Verified: all 75 `tier: none` entries have `nav_label: null`; all 32 non-`none` entries have a `nav_label`.
- **`description` is user-facing prose. `notes` is developer shorthand and stays untouched** — it currently holds text like "absorbs discovery-inbox, discovery-review, archive-panel", which must never reach a tooltip.
- **Do not migrate the 34 files using ad-hoc `title=`.** Separate cleanup; bundling it couples an accessibility refactor to a docs feature.
- **Screenshots are build artifacts. Never commit a PNG.**
- **`surfaceRegistry.generated.ts` and `gui-surfaces.generated.md` are generated — never hand-edit.** Both are regenerated by `vox ci gui-surface-registry --write`, which is in the `ssot-autoregen` bot's write set, so a hand edit will be silently overwritten on the next PR.
- **Verification tier is `--full`**, not `--complete` (`--complete` runs no tests).
- **Line endings LF** for `rs`, `ts`, `tsx`, `md`, `yaml`.
- **No checker enters this plan until it has been run against the real tree and its actual output pasted into the step.**
- **One agent per worktree.**

The blocking prerequisite. The gate in Task 3 cannot turn on until every real

- [ ] **Step 1: List exactly which entries need one**

```bash
python -c "
import re
t=open('contracts/gui/surface-registry.v1.yaml',encoding='utf-8').read()
for e in re.split(r'\n- view_key: ', t)[1:]:
    key=e.split('\n')[0].strip()
    tier=re.search(r'representation_tier: (\S+)', e).group(1)
    nav=re.search(r'nav_label: (.+)', e)
    if tier!='none':
        print(f'{key:24} {tier:18} {nav.group(1).strip() if nav else \"?\"}')
" | tee /tmp/surfaces.txt | wc -l
```

Expected: **32** lines. If the count differs, the registry changed since this
plan was written — use the real list, and note the deviation in your report.

- [ ] **Step 2: Read each surface's component to describe it accurately**

For each `view_key`, the implementing component is under
`crates/vox-gui/ui/src/components/surfaces/`. Find it:

```bash
ls crates/vox-gui/ui/src/components/surfaces/
```

**Do not write descriptions from the `nav_label` alone.** A label like
"Mercatus" or "Scientia" tells a user nothing; the description exists precisely
to explain what the label does not. Read the component (and its `notes:` field
for context, without copying it) before writing.

- [ ] **Step 3: Add `description` to each of the 32 entries**

One or two plain sentences, addressed to a user, saying what the surface is
*for* — not how it is built. Place the key after `nav_label`. Use YAML folded
scalars for anything over ~80 chars:

```yaml
- view_key: chat
  cli_group: null
  representation_tier: live_backend
  nav_label: Chat
  description: >-
    Send instructions to an agent and watch its replies stream back. The
    session rail keeps prior conversations so you can return to one.
  nav_icon: send
  nav_group: operate
  parent_surface: null
  notes: Primary chat surface
```

Rules, because these strings ship to users:
- No internal crate names, no `view_key`s, no migration history.
- No "This surface allows you to…" — say what it does.
- Present tense, active voice.
- If a surface is genuinely a stub with no behavior yet, say so plainly rather
  than describing an aspiration — an honest "not yet wired" beats a
  description of something that does not work. Cross-check against
  `docs/agents/gui-honesty-findings/` if unsure; several surfaces are
  documented there as incomplete.

- [ ] **Step 4: Confirm the YAML still parses and no `tier: none` entry gained one**

```bash
python -c "
```

Expected: `missing description: []` and `tier=none WITH description: []`.

- [ ] **Step 4: Add the field and emit it**

In `SurfaceEntry`, after `notes`:

```rust

    /// rendered on the generated docs page. Required for every surface whose
    /// `representation_tier` is not `None`; forbidden otherwise (those entries
    /// are CLI-group placeholders, not screens). Distinct from `notes`, which
```

In the TS interface string, add `  description: string | null;\n` after
`parentSurface`. In the row `format!`, add `, description: {}` and pass

containing an apostrophe ("agent's") would break the generated TS. Read `opt`'s
body; if it does not escape, either escape within `opt` or ensure Task 1's
descriptions avoid apostrophes — **prefer fixing `opt`**, since a contract
field that silently corrupts generated code on a common character is a trap for
the next person. Add a test with an apostrophe either way.
