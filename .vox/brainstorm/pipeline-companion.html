3 · The three gaps this brainstorm targets

Gap A — Boundary is convention, not language. @native is a token that is Unverified on every target (no semantics). Nothing stops a perf function from being expected in TS, or a GUI component from being called server-side. The placement of code is decided by humans + CLI flags, so it can't be checked.
Gap B — The Rust arm is slow and has no middle gear. Two speeds only: interp (~50ms, no native perf) and full cargo AOT (cold builds dominate). No incremental/JIT tier; vox-db is the #1 build-blast-radius keystone.
Gap C — Parity proves emission, not agreement. A feature can emit on both Rust and TS yet behave differently. There is no differential oracle asserting interp ≡ Rust ≡ TS on the same input.

4 · Open design questions

1

Scope — one spec or three?

A. Treat A/B/C as one program, decompose into 3 sub-specs (boundary → speed → parity-oracle), brainstorm the first now.my lean
B. Pick the single highest-pain gap and go deep on only that one today.
C. One combined spec covering all three.
2

Gap A — how do we represent "perf-native vs GUI" at the language level?

A. Status quo+docs: keep convention + --target flags, just write it down. (cheapest, no enforcement)
B. First-class placement decorators — promote @native/@gui (or @server/@client) to compiler-enforced placement; a function's placement decides which backend(s) MUST emit it, and cross-placement calls become a checked RPC/boundary.my lean
C. Infer placement from the existing effect/capability system (@pure, @uses(net), JSX usage) — derive it, annotate only the exceptions.
D. Combo: infer by default (C) with an explicit override decorator (B) when inference is wrong.
3

Gap B — what's the new "middle gear" for speed?

A. Make interp the default dev loop; Rust AOT only on --release/explicit. (reuses what exists)
B. Invest in incremental/warm cargo (build-broker L1 + cached codegen + split the vox-db keystone).
C. Add a real JIT tier (Cranelift/WASM) between interp and AOT — native-ish speed, no cargo.
D. A + B together (interp-default now, broker as the durable win), JIT deferred.my lean
4

Gap C — what does "guaranteed at parity" mean to you?

A. Emission parity — every construct compiles/emits on each declared target (≈ what you have). Cheap, already mostly built.
B. Behavioral parity — a differential oracle runs the same fixture through interp + Rust + headless-TS and asserts equal observable output.my lean
C. Both, tiered: emission gate stays blocking; behavioral oracle runs on the canonical ladder + grows over time.
5

How should a NEW language element be forced into the pipeline?

A. Keep the compile-time exhaustive matrix as the sole gate (add feature → won't compile until every cell filled).
B. Matrix + a required ladder fixture per new feature (CI fails if a feature has Implemented but no proving fixture).my lean
C. B + a "parity dashboard" generated from the matrix/ladder so drift is visible, not just red CI.
